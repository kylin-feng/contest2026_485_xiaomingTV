## 1. 证据一：app 真的进了固件（消掉静默符号抢占）

### 1.1 症状（修复前）

板级 `bsp_voice_link.c` 与 app `mianyu_app_main.c` **各自定义了一个
`int mianyu_main(int argc, char *argv[])`**。`CONFIG_INIT_ENTRYPOINT = mianyu_main`，
链接器解析 init 入口时先撞上板级那个目标文件，于是 app 的
`mianyu_app_main.o` **整个没被从静态库拉出来** ——
`libapps_mianyu.a` 里所有成员都跟着被丢弃。

编译日志全绿、`ninja` 退出码 0，但固件里没有哄睡主循环。
旧固件（`nuttx_audio11.bin`）的启动日志里出现的是板级那行：

```
[vlink] mianyu_main: 产品模式启动（无 nsh 控制台，串口归语音链路独占）
```

—— 这是**假通过**：日志有、逻辑无。

### 1.2 处置

板级函数改名为 `vl_product_hold()`（仅作兜底：万一 app 没编进来，由它占住 init
线程，避免系统因没有 init 入口跑飞）。语音链路本来就不依赖这个符号 ——
它由 `board_late_initialize()` 里的 `bsp_voice_link_start()` 独立拉起。

### 1.3 修复后核对（`nm nuttx`）

```
$ nm nuttx | grep -E " (T|t) (mianyu_main|vl_product_hold)$"
1202cced T mianyu_main                 # 只剩一个，来自 app

$ nm apps/packages/demos/contest2026_485_mianyu/.../mianyu_app_main.c.o | grep mianyu_main
00000001 T mianyu_main                 # 确证这个符号出自 app 目标文件
```

`vl_product_hold` 已被 `--gc-sections` 丢弃（无引用）—— 说明 app 的入口
真被选中了，兜底没派上用场。

### 1.4 app 侧符号全部在位

```
12031a3d T my_breathe_init
12030209 T my_fade_init
120325b5 T my_hal_audio_play
12032615 T my_hal_light_set
12030e0b T my_mem_init
1202e1c9 T my_sched_init
1202f449 T my_sleep_init
```

### 1.5 体积交叉验证

| 固件 | 大小 | 说明 |
|---|---|---|
| `nuttx_audio11.bin`（修复前） | 1,571,940 B | app 未链接 |

## 3. 证据三：语音链路在线（板 → PC 持续上行）

板上运行 20 秒后，链路心跳行（混在二进制 PCM 流里，需从原始字节流抠）：

```
[vlink] 上行 672 帧 下行 0 帧 | 麦克风 HT=84 TC=84(Δ8) | 待放=0 样本 |
        TX 350277 字节 丢帧 0 | CRC错=1 重同步=3 | cfg=MIC-UP
[vlink] 上行 704 帧 下行 0 帧 | 麦克风 HT=88 TC=88(Δ8) | 待放=0 样本 |
        TX 366949 字节 丢帧 0 | CRC错=1 重同步=3 | cfg=MIC-UP
```

| 指标 | 读数 | 判读 |
|---|---|---|
| 上行帧数 | 672 → 704（20 s 内 +32 帧） | 帧率 ≈ 1.6 帧/s，稳定推进 |
| 丢帧 | **0** | 上行零丢帧 |
| CRC 错 / 重同步 | 1 / 3 | 仅开机握手期出现，之后不再增长 |
| TX 字节 | 350,277 → 366,949 | ≈ 833 B/s ≈ 上行 PCM 实际带宽 |
| 麦克风 HT/TC | 84/84 → 88/88 | MIC 链路有稳定计数（HT=半满, TC=全满） |
| `待放=0 样本` | 下行缓冲空 | 本轮未发下行音频，符合预期 |

**结论**：板子作为「耳朵 + 嘴 + 按键」的串口链路在真机上是通的，
且上行对丢帧敏感的部分（PCM）实测零丢帧。

## 4. 证据四：喇叭声学输出 —— **未通过**（如实记录）

### 4.1 方法：声学回环对照法

放**板上本地** 1 kHz 音源，测麦克风收到的 1 kHz 能量，做两组对照：

- **B 组：功放使能**（PA10 = 1）→ 喇叭若发声，麦克风应额外收到「空气传播」的 1 kHz
- **C 组：功放关闭**（PA10 = 0）→ 只剩板内 DAC 输出结点 → MIC 的**电耦合**

判据：若 `C 组 ≈ B 组`，说明麦克风里的 1 kHz **全部来自电耦合**，喇叭没出声。
每组 12 窗累加（≈0.8 s）压方差 —— 单窗读数跳动太大（1 kHz 64 vs 邻近 21~37），
不可判。

### 4.2 结果（`sound_card.py`，多窗平均）

| 组 | 放音 1kHz | 邻近 (750/1250 Hz) | 1kHz / 邻近 |
|---|---|---|---|
| B 功放开 | 73.5 | 9.5 | 7.74× |
| C 功放关 | **88.5** | 9.5 | 9.32× |

**B / C = 0.83** —— 关掉功放之后 1 kHz 反而更高。

### 4.3 判读

- 麦克风确实收到了很强的 1 kHz（1kHz/邻近 ≈ 8~9×，远超 4× 判据）→ **DAC 输出通路是活的**
- 但**功放使能与否对读数没有正向贡献**（0.83×）→ 这 1 kHz 是
  **DAC 输出结点 → MIC 通路的板内电耦合**，不是空气传播的声波
- 功放使能后读数略降，符合「功放输入级加载了 DAC 输出结点、串扰略降」的物理直觉

**结论：喇叭（J0101）基本没有发出声波。板内音频电通路正常，声学输出未通。**

### 4.4 已排除项 / 待确认项

| 项 | 状态 |
|---|---|
| `BSP_ENABLE_DAC2` | 仅 LB58X 定义；LB52 的 DAC2 禁用 —— **设计如此，非缺陷** |
| DAC1（A.33）输出级 `EN_OS_DAC` | 已开 |
| 功放使能脚 PA10 | pinmux `HAL_PIN_Set(PAD_PA10, GPIO_A10, PIN_PULLDOWN, 1)` + 运行期拉高，**已确认置位** |
| 功放芯片 U0104（NS4150B） | 软件侧无更多可控项（无 I²C 配置） |
| **接插件 J0101 是否插了喇叭** | 🔴 **需人工确认** —— 当前最可能的原因 |

> 下一步（需动手）：确认 J0101 上是否接了喇叭。插上后重跑 `sound_card.py` 复验，
> 若 B/C 比从 0.83 跃升到 2× 以上即判定声学通路打通。

## 5. 复现步骤

```bash
# 1. 云机编译（算力卡）
ssh -p 40131 root@connect.nmb1.seetacloud.com
cd /root/vela && source build/envsetup.sh && cd cmake_out/sf32lb52_devkit_lcd && ninja
# 产物 nuttx.bin

# 2. 取回 + 烧录（PC 侧）
sh $TEMP/xm-scp.sh root@<host>:/root/vela/cmake_out/sf32lb52_devkit_lcd/nuttx.bin ./nuttx_audio12.bin
./sftool.exe -c SF32LB52 -p COM6 -b 1000000 write_flash nuttx_audio12.bin@0x12010000

# 3. 抓启动日志 + 判读
python sniff_boot.py COM6 22 bootlog_app_v12.txt

# 4. 声学回环复验（需板子已接喇叭）
python sound_card.py
```
