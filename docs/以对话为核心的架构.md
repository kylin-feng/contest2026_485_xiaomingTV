# 以语音对话为核心的架构

这篇讲清楚一件事：**为什么这台设备的核是 Agent 语音对话，入睡判定和呼吸光引导是附加。**
以及这个定位落到接口上是什么样。

写这篇是因为一开始我们的定位是反过来的 —— 讲"主动闭环、无任何用户指令、
全由 cron 和传感器驱动"（`docs/系统框图与数据流图.html` 里还留着那个说法）。
那个讲法技术上没错，但把重心放错了：**它把 Agent 讲成了一个定时器。**

---

## 1. 第一性原理：先看约束

不要先想"要做什么功能"，先看这东西被什么约束着。

| 约束 | 后果 |
|---|---|
| 人在黑暗里躺着，闭着眼 | **不能按按钮，不能看屏幕。** 交互入口只剩声音 |
| 睡不着的原因每晚都不同 | **固定流程覆盖不了。** 今天脑子停不下来、明天要交东西、或者就是闷 |
| 半睡状态下对声音反感、对光接受度高 | 需要一条**不占用耳朵**的输出通道 |
| 目的不是"提供信息"，是"让人睡着" | 设备说错话的代价不对称：多一句"晚安"就能把人弄醒 |

把这四条摆在一起，结论只有一个：

> **唯一能承载这些约束的交互形态是对话 —— 你说，它听懂；它说，你了然。**
> 而且它必须知道**什么时候该闭嘴**，这是对话能不能用于哄睡的分界线。

## 2. 反面论证：如果核心不是对话会怎样

假设核心是"定时器 + 传感器"：22:30 放白噪音，检测到呼吸平稳就淡出。

那么这台设备需要什么？一个 RTC、一个麦克风、一个滤波器、一个渐弱曲线。
**不需要 LLM、不需要 Agent、不需要记忆。** 任何一台几十块的白噪音机都能做，
做得可能还更稳（没有识别延迟、不会理解错）。

所以这不是"我们顺便也支持对话"，而是：

> **AI 的价值全部集中在"能对话"这一件事上。**
> 不是对话的话，这个作品就没有存在的理由。

## 3. 回路：一个核心 + 它的两端

```
                    ┌──────────────────────────────────────┐
                    │        Agent（大脑，LLM 上跑）        │
                    │  3 个 Skill：sleep-onset / night-wake │
                    │              / sleep-review           │
                    └───────┬──────────────────────┬───────┘
                            │  读：现在什么状态？   │  写：该做什么？
              ┌─────────────▼────────────┐   ┌─────▼──────────────────┐
              │ 附加 1 · 入睡判定（输入） │   │ 附加 2 · 呼吸光引导（输出）│
              │  呼吸规律度 reg / 体动    │   │  4-7-8 节拍 + 亮度      │
              └─────────────▲────────────┘   └─────┬──────────────────┘
                            │                       │
                     MEMS MIC（听）            AMOLED 光晕 + DAC→功放（说）
```

三个位置各自不可替代：

- **没有核心**：两个附加什么都不是 —— 判定出来的数字没人用，光自己在那儿亮，就是台闹钟。
- **没有附加 1**：Agent 只能靠计时器猜"该停了吗"。它说的话就不是判断，是播放列表。
- **没有附加 2**：Agent 手上只有一个通道（说话）。要引导呼吸就只能一直说，而说话本身吵人。

所以正确的说法是：

> **核心是对话；两个附加是这条对话回路缺一不可的两端。**
> 它们不是"三个并列的功能"，是「一个核心 + 它的输入和输出」。

## 4. 核心怎么落地

### 4.1 行为写在 Skill 里，不写在代码里

`skills/` 下三个 Skill 是标准 Agent Skill 格式（`When to use` / `How to use` /
`Important` / `Example`），直接给 Agent 读，调用 `get_current_time`、`music_play`、
`music_set_volume`、`read_file` 这些工具。

关键的一点：**哄睡的知识写在提示词里，不是硬编码成 if-else。**
比如 `night-wake` 里的禁忌清单（不提问、不报时间、不聊天、30 分钟内不重复同一话术），
这些是经验判断，写成 C 代码就是一堆魔法数字，写成 Skill 就是可读、可改、可解释的规则。

改话术、换策略不用重新烧固件 —— 这是 Agent 架构在这个场景里最直接的好处。

### 4.2 主动性由 Agent 承担，不是 cron 承担

原来的讲法是"主动性 = cron 引擎到点触发"。重新想一遍：cron 只是**触发条件之一**，
真正的主动性体现在 Agent 会自己决定**要不要开口、开口说什么**。

触发条件有三类，全交给 Agent 判断：

| 触发 | 例子 | Agent 的反应 |
|---|---|---|
| 定时 | 22:30 到点 | 轻声开场（一句，说完就等回应） |
| 阈值 | 长时间未入睡 | 换策略（读记忆里最快入睡的手段） |
| 事件 | 夜间体动 / 用户出声 | 最轻干预，不追问 |

**它不等唤醒词**，这是和普通音箱的分界。但这个"主动"是**有判断的主动**：
到点了它先看距你计划睡前还剩多久，超过 15 分钟只轻声提醒、不启动完整流程。

### 4.3 记忆是 Agent 的一部分

180 天滚动档案（入睡潜伏、夜醒次数、哪种手段最快入睡）全在端侧。
它的用法不是"给你看报表"，而是**喂给 Skill 做决策**：
`sleep-onset` 开场前读 `best_aid`，今晚优先用你历史上最快入睡的那个手段；
`sleep-review` 晨起读出来，说"你昨晚 22:52 睡着的，比前天早半小时"
（比报"总时长 6h40m"像人得多 —— 报数据是体检报告，说"比前天早"才是说话）。

## 5. 附加 1 · 入睡判定：接口现状

### 5.1 它给 Agent 提供什么

一个数和一个结论：

- **呼吸规律度 reg**（0~1）—— 归一化自相关在 0.15~0.5Hz 范围内的峰高
- **呼吸率** —— 峰位换出来的次/分（9~30 范围）
- **体动强度** —— RMS 包络的高频分量
- **状态**（清醒 / 入睡中 / 已睡着）—— 迟滞状态机输出的结论

Agent 拿到这些才能说"我感觉到你慢下来了"，而不是"30 分钟到了"。

### 5.2 为什么不在板子上做决策

判定跑在板子上（`src/mianyu_sleep_detect.c`，平台无关纯 C），
但**决策不跑在板子上**。理由很实在：

- 板子主核**没有独立 DSP**，跑时域分析已经是上限了，跑不了 LLM
- 判定阈值需要个体化（每个人呼吸幅度、入睡潜伏都不一样），
  个体化要读记忆、要结合上下文 —— 那是 Agent 的活
- 板子只负责**如实上报观测值**，不做"我觉得你睡着了"这种越权判断

### 5.3 接线状态（重要，如实说明）

链路协议（`board_link.py`）现在有这些帧类型：

| 码 | 名称 | 方向 | 现在干什么 |
|---|---|---|---|
| `0x01` | AUDIO_UP | 板→PC | MIC 采到的 PCM（16k/16bit/mono） |
| `0x02` | AUDIO_DOWN | PC→板 | 送去喇叭播的 PCM |
| `0x03` | EVENT | 板→PC | 按键 / 启动完成（`EV_KEY_DOWN` / `EV_KEY_UP` / `EV_BOOT_READY`） |
| `0x04` | CMD | PC→板 | 功放开关 / 音量 / 打断 / MIC 开关 / 提示音 / 下行开关 / 回环自检 |
| `0x05` | PING / PONG | 双向 | 保活 |
| `0x06` | LOG | 板→PC | 调试文本 |

**这条线已经接上了**（新增 `EV_SLEEP_STATE` = `0x04`）：

| 码 | 名称 | 方向 | 载荷（实际实现） |
|---|---|---|---|
| `EV_SLEEP_STATE` | 判定状态变化 | 板→PC | `[0x04, state, conf%, bpm]`，`state: 0=清醒 1=困倦 2=已入睡` |

发送时机：**状态跳变即发**，另外每 5 分钟补一次心跳。一晚实测约 113 条
（整晚 30600 秒），够证明板子还活着，又不占带宽 —— `AUDIO_UP` 已经占了
16kHz×16bit = 32 KB/s，而判定帧只有 14 字节。

**没有单独做 `EV_SLEEP_TICK`**：判定本来就是每 2 秒才更新一回，再单开一条
低频心跳是重复的。心跳帧里带 `state + 置信度 + 呼吸率`，要看细粒度曲线走 `LOG` 帧。

> **诚实边界**：以上只有**编译期证据** —— 四个新符号都进了 `System.map`、
> 提示串进了镜像、链接无 undefined。**没做过真机联调**（板子/喇叭还没就绪），
> 上行帧能否被 PC 实际收到、丢帧率多少，都还是未知数。

## 6. 附加 2 · 呼吸光引导：接口现状

### 6.1 它给 Agent 提供什么

一个**不占用耳朵**的输出通道。Agent 说"跟着我呼气"，同时光晕在呼气段变暗 ——
两条通道说同一件事，用户闭着眼也能跟上。

`src/mianyu_breathe.c` 是独立节拍器引擎，跑 4-7-8（吸 4s / 屏 7s / 呼 8s，19 秒一周期）。
它必须严格、可重复、不刺眼（理由见 `mianyu_breathe.h` 头部注释）：
段边界用 smoothstep 保证首尾导数为 0，允许配谷值亮度（呼气底不全灭，
避免"灯灭了"的突兀感），夜间模式把峰值压到 ~30%、谷值 ~4%。

引擎不调用任何 OS 时间函数，时间由调用方 `tick(delta_ms)` 喂入 ——
所以 PC 上能完整单元测试（`tests/test_breathe.c`，41 条断言）。

### 6.2 接线状态

**这条线也已经接上了**，是三个码：

| 码 | 名称 | 方向 | 载荷（实际实现） |
|---|---|---|---|
| `CMD_SET_BREATHE` | 设定呼吸节拍 | PC→板 | `[0x08, inhale(2 LE), hold(2 LE), exhale(2 LE), peak%]`，时长单位 ms |
| `CMD_SET_HALO` | 只改光晕峰值 | PC→板 | `[0x09, peak%]` |
| `CMD_LIGHT_ONOFF` | 开 / 关灯 | PC→板 | `[0x0A, on]` |

链路侧收到只做**入队**，真正的落地在主循环里 —— 只有它知道灯现在亮不亮、
呼吸引擎在哪个相位。两个线程同时改一个引擎是要出鬼的。队列满时丢最旧的一条：
光引导是"最新的一条说了算"，积压旧命令只会让光乱跳。

顺带说清一个跨线程的取舍：`vl_send` 组帧用的 `g_tx_seq` 不是原子的、写串口
也不能交错，它本来是给链路线程**单写者**用的。所以判定上行**不是**直接调
`vl_send`，而是入队后由链路线程在下一拍代发（延迟上限 ≈16ms，对秒级的判定
信号无所谓）。音频热路径一行没动。

接上以后能做的事就变得有意思了：Agent 可以**按对话内容换节拍** ——
用户说"心里有点堵"，就换成更慢的呼（吸 4 / 呼 12）而不是标准 4-7-8。

## 7. 和旧说法的差别（诚实记一笔）

| | 旧讲法 | 现在的讲法 |
|---|---|---|
| 核心 | 主动式调度（cron 驱动整晚） | **Agent 语音对话** |
| Agent 的角色 | 整晚流程的执行者 | **大脑，做所有决策** |
| 入睡判定 | 核心能力之一（第 2 条） | **附加：核心的输入端** |
| 呼吸光引导 | 塞在"手表界面"里讲 | **附加：核心的输出端** |
| 主动性 | cron 到点触发 | **Agent 有判断地开口** |
| 噪声合成 / 记忆 | 独立能力（第 4、7 条） | 分别归入核心的**输出实现**与**记忆** |

技术内容一条没少，改的是重心：**从"设备有哪些功能"改成"设备靠什么活着"。**

代码侧这个调整的落点是 §5.3 和 §6.2 里那四个帧码 —— 判定结果上行、光引导下行。
把这四个码接上，"对话为核心"就从架构主张变成跑得起来的东西。

## 附：这几个附加单独存在的价值

顺手回答一个常被问到的问题："既然判定和光引导是附加，那单独做它们行不行？"

- **判定单独存在**：算出 reg=0.72、呼吸 14 次/分，然后呢？没有人在读这些数，
  它只能自己拿去做阈值判断 —— 那就是回到了"定时器+传感器"的老路，不需要 AI。
- **光引导单独存在**：灯在自己呼吸，挺好看。但用户为什么会跟着它呼吸？
  因为有人（Agent）说了"跟着光"。没人说这一句，它就是装饰灯。

**两个附加的价值完全来自被核心调用。** 这就是它们"附加"的准确含义 ——
不是不重要，是**不能独立成立**。
