## 先说结论

手表界面（表盘页 + 哄睡页）**已经进了固件，在板上跑起来了，触摸也能用**。
碰到的两个真问题都定位到根因并修掉了：

1. **触摸一直连不上** —— 不是驱动的问题，是**注册时序**：FT6146 在开机后
   约 23 秒才把 `/dev/input0` 注册出来，而 LVGL 在 15 秒就起来了。
2. **界面卡到 5 fps** —— 不是刷屏慢，是 `lv_label_set_text()` 每帧无条件标脏。
   flush 实测只要 6µs，脏区却到了 66432 像素/帧。

**还没做的**：屏幕肉眼确认。串口能证明对象建好、渲染循环健康、触摸挂上，
但证明不了"你眼睛看到的是对的那一幅画"。这一条留给人工看板（见第 5 节，
并且第 5 节记了一条板级诊断，说明为什么这件事不能靠日志下结论）。

## 1. 界面是怎么设计的

两个页面，能点的地方只有两个。

| 页面 | 上面有什么 | 进去 / 出来 |
|---|---|---|
| 表盘页 | 大时间、日期、今晚计划（几点自动开始）、一个「开始哄睡」按钮、昨晚简报 | 开机默认停这 |
| 哄睡页 | 中间三层呼吸光晕、上面一行当前阶段、底部噪声类型 + 已用时、左上「返回」 | 点按钮进来 |

交互上就想清楚了三件事：

- **点「开始哄睡」立刻切页**，不等后台确认。表盘上按下去 100ms 才切，手感上
  就是"没反应"。
- **点「返回」只回表盘，哄睡继续跑**。设备正在哄睡，用户按回表盘看一眼时间，
  不该顺手把声音和判定一起停掉 —— 这是最容易被写错的地方。按钮这时改写成
  「回到哄睡」。
- **长按「返回」才是真的结束今晚**（停声音、复位判定）。破坏性动作用长按。

夜里不刺眼这条落在配色上：AMOLED 底色用纯黑 `000000`（纯黑像素不发光，
一点光都不漏），文字和光晕只用暖色 `FFB26B`（约 2700K），不用蓝白。
睡着之后整屏压暗、文字不再更新，只留一层很淡的呼吸感。

热区都不小于 68×40，最小字号 16 —— 手表屏小、手指粗，这条不做用户会点不中。

## 2. 触摸为什么连不上，怎么修的

### 现象

界面对象全建出来了（`objs=2`），但 `indev=0`，点屏幕没反应。
`lv_nuttx_init()` 那一行还带着 `errno=2`。

### 查出来的原因

两个叠在一起：

**第一个**：`lv_nuttx_dsc_init()` 会**默认**把 `dsc.input_path` 指到
`/dev/input0`。我们照着默认用，LVGL 初始化时就去 open 这个节点 —— 那一刻它
还不存在，于是 `errno=2`。

**第二个（真正的坑）**：FT6146 注册得**很晚**。板级那条 lcd 线程要先把 co5300
一长串初始化命令发完、面板自检跑完，才轮到 ft6146 去
`touch_register("/dev/input0")`。实测时间线：

```
t=15.26s  LVGL: lcd /dev/lcd0 open success
t=23.10s  ft6146: touch_register ret=0      ← 触摸节点这时候才出现
```

LVGL 15 秒就起来了，触摸 23 秒才到。原来的写法是"启动时等 5 秒，等不到就
永远没有触摸" —— 差的就是这 8 秒。**这是典型的后到设备问题，一次性判定必然错。**

### 怎么修的

触摸改成**运行期探测 + 补挂**：LVGL 线程每 500ms 探一次 `/dev/input0`，
节点一出现立刻 `lv_nuttx_touchscreen_create()` 挂上；同时把
`dsc.input_path` 显式清成 `NULL`，不让 `lv_nuttx_init` 去打那行没用的 `errno=2`。

```
static bool my_dev_exists(const char *path) {          /* 只探，不等 */
    int fd = open(path, O_RDONLY | O_NONBLOCK);
    if (fd < 0) return false;
    close(fd); return true;
}

if (indev == NULL) {
    uint32_t t0 = lv_tick_get();
    if ((uint32_t)(t0 - last_probe) >= 500) {
        last_probe = t0;
        if (my_dev_exists("/dev/input0")) {
            indev = lv_nuttx_touchscreen_create("/dev/input0");
            if (indev) lv_indev_set_display(indev, res.disp);
        }
    }
}
```

### 修的过程中又踩了一个

第一版计时写成 `since_probe += lv_timer_handler()`，结果**触摸 110 秒才挂上**。

原因：`lv_timer_handler()` 的返回值是**"建议下次被调用的间隔"**，也就是这一帧
渲染花了多久 —— 这块屏一帧一百多毫秒时它是 100 量级。拿它当毫秒累加，等于把
"每 0.5 秒探一次"放大成了"每 110 秒探一次"。LVGL 里唯一能当真实毫秒用的是
`lv_tick_get()`。

修完的日志（`nuttx_clean1.bin`）：

```
[LVGL] [User] (23.144, +7879)  lv_nuttx_touchscreen_create: touchscreen /dev/input0 opening
[LVGL] [User] (23.149, +5)     lv_nuttx_touchscreen_create: touchscreen /dev/input0 open success, maxpoint 1
[mianyu] 触摸已补挂 indev=0x20044478
```

## 3. 界面为什么卡到 5 fps，怎么修的

### 现象

呼吸光晕肉眼看是一顿一顿的。加了个临时探针量出来：**196ms 一帧，5 fps**，
而且 LVGL 那条线程一直吃满 CPU，还挤主循环。

### 排除了两个嫌疑人

一开始怀疑两件事，都量了，**都不是**：

| 怀疑 | 怎么量的 | 结果 |
|---|---|---|
| 整屏渲染太贵 | 改成局部刷新缓冲（390×48，`LV_DISPLAY_RENDER_MODE_PARTIAL`） | 帧率一点没变，还是 196ms |
| flush 到屏太慢 | 在 `flush_cb` 里量 `LCDDEVIO_PUTAREA` ioctl 耗时 | **6µs/次**，可以忽略 |

那就只有第三个可能了：界面自己在整屏重画。挂一个
`LV_EVENT_INVALIDATE_AREA` 回调累计脏区面积 —— **66432 像素/帧**，
一屏是 390×450=175500，也就是说每帧重画了三分之一屏的东西，而画面上真正
在变的只有呼吸光晕那一圈。

### 根因

`lv_label_set_text()` 是**无条件** `lv_obj_invalidate()` 的，并且每次都会
free 掉旧文本缓冲再 malloc 一个新的 —— 哪怕你传进去的字符串和上次一模一样。

主循环 10Hz 推快照，界面 10Hz 刷新，每次刷新都把时间、日期、计划、昨晚结果、
阶段、噪声类型、已用时……**全套 8 个标签**重设一遍文字。于是每帧全屏重画
三分之一，还顺带 8 次 malloc/free。

### 怎么修的

加一层"值没变就一个 LVGL 调用都不发"的缓存：

```c
/* 和上次一样的文本，一个 LVGL 调用都不发 —— 见 docs 里根因说明 */
static void set_text_if_changed(lv_obj_t *l, char *cache, size_t n, const char *txt)
{
    if (strncmp(cache, txt, n) == 0) return;
    snprintf(cache, n, "%s", txt);
    lv_label_set_text(l, cache);
}
```

配三件事：

1. **每个标签配一个缓存字段**（`c_time` / `c_plan` / `c_phase` / …），
   值一样就直接返回。
2. **光晕透明度量化**：外圈 16 档、中圈 8 档、内核 1 档。透明度是浮点算出来的，
   每帧差 0.3 也会标脏；量到档位上，没跳档就不发。
3. **按钮文字和描边色只在 `running` 翻转时改**，不是每帧改。

### 修完的数字

| 场景 | 修之前 | 修之后 |
|---|---|---|
| 表盘页静止 | 24 帧 / 5s（197ms/帧） | **125 帧 / 5s（~0ms/帧）** |
| 表盘页脏区 | 整屏级 | **0 像素** |
| 哄睡页（呼吸光晕在跑） | — | **121 帧 / 5s（2ms/帧）** |
| 哄睡页脏区 | — | **1027 像素/帧**（每拍只重绘内核） |

表盘页静止时脏区 0 是这次优化最直接的证据：**没有任何变化 → 一次刷新都不发**。

## 5. 还没做的：屏幕肉眼确认（以及为什么不能靠日志下结论）

到这里能说的都说了。但**"屏幕上到底亮成什么样"这件事，日志证明不了**。

而且这一版日志里有一条板级诊断，正好说明为什么：

```
[co5300][readback] GRAM(0x2E)=7f 00 00 7f -> NO MATCH -> pixel data is not landing (QSPI write/mode)
```

这是板级 co5300 自检里"写 GRAM 再读回来比对"那一步，读回来的和写进去的对不上。
**这条在之前每一版固件里都有**（09-13 到 09-15 的日志都能 grep 到），不是这次
改出来的。

它有两种解释，日志本身分不出来：

- **坏解释**：QSPI 写像素真的没落进面板 GRAM，屏上是空白/花的。
- **大概率解释**：CO5300 走 QSPI 时 GRAM 读回本来就不受支持，读回来的是哑数据，
  这条自检是**假警报**。同一个 log 里 `[co5300][probe] ID len1=0x33 len2=0x3311
  len3=0x331100 len4=0x33110000` —— 同一个 ID 在 4 个字节偏移上错位重复，
  这正是"读通路有位移"的典型样子。

我不打算靠猜把这条写成"屏是好的"。**要人工看一眼**，方法很简单：

上电重启，按这个顺序看屏：

1. 开机瞬间应该有**纯色闪过**（`[co5300][cmdtest]` 那步在刷全白 → 全红 → 全绿 → 全蓝），
   跟着背光 `PA01` 会亮灭三次。**看得到闪色，就说明像素通路是通的**，那条
   readback 就是假警报。
2. 然后停在**表盘页**：大时间、日期、「开始哄睡」按钮。
3. 手指点「开始哄睡」→ 应立刻切到**哄睡页**，中间三层呼吸光晕在缓慢明暗。
4. 点左上「返回」→ 回表盘，按钮文字应变成「回到哄睡」。
5. 长按「返回」→ 结束今晚。

第 1 步是关键分水岭：**看到闪色 = 显示通路没问题，剩下全是界面逻辑；
看不到闪色 = 得回去查 QSPI 写模式，跟界面无关。**

## 7. 这一轮踩过的坑（给后面接手的人）

| 坑 | 现象 | 真因 |
|---|---|---|
| 触摸永远连不上 | `indev=0`、`errno=2` | FT6146 开机后 ~23s 才注册 `/dev/input0`，LVGL 15s 就起来了；一次性等 5 秒必然失败 |
| 触摸 110 秒才挂上 | 探到了但特别晚 | 拿 `lv_timer_handler()` 返回值当毫秒累加，那是帧渲染耗时；必须用 `lv_tick_get()` |
| 局部刷新缓冲没用 | 改了帧率一点不变 | 瓶颈不在渲染量，在 `lv_label_set_text` 每帧无条件标脏 |
| `make` 报 No targets | 云机构建失败 | 构建目录是 ninja 生成器，得用 `ninja` |
| `arm-none-eabi-ar: not found` | 编译中断 | 工具链不在默认 PATH，得先 export |
| `mingw32-make test` 找不到 `cc` | Windows 评审第一步就卡 | `CC` 是 make 内建变量（默认 `cc`），`CC ?=` 永远不生效；改成按平台 `:=` 赋值 |
