# 安眠科技 · 主动式哄睡智能体

openvela AI 硬件开发者大赛 2026，队伍 485 小鸣TV。目标板 SF32LB52-DevKit-LCD。

## 它是干什么的

放在床头的哄睡设备。22:30 自己开口引导入睡，感觉到你睡着了就慢慢把声音收到零；
半夜醒来它不亮屏，用很小的声音接住你；睡过几晚之后，它记得你吃哪一套。

**跟智能音箱最大的区别是它不等你开口。** 普通音箱你问它才答，
这台设备整晚不需要你说任何一个字，全靠定时和传感器事件自己往下走。

## 核心能力

**1. 主动式调度，不依赖用户指令**

整晚的流程由 cron 引擎驱动：到点开始哄睡、判到入睡就淡出、检测到夜醒就安抚、
早上渐亮并给出昨晚的记录。四类主动任务（定时 / 阈值 / 事件 / 上下文）都落地了，
这是 openvela ai_agent 主动任务能力的完整用法。

**2. 不用 DSP 的入睡判定**

目标板主核没有独立 DSP，跑不动频域分析。所以走时域：
100ms 帧算 RMS 包络，降到 10Hz，在 30 秒窗里做归一化自相关，
在 0.15~0.5Hz（对应 9~30 次/分）的滞后范围找峰 —— 峰高就是呼吸规律度，峰位就是呼吸率。
再配一个迟滞状态机防抖。

算一次大概 18000 次乘加，每 2 秒算一回，占空比不到 0.05%。
465 条断言全绿，混淆矩阵 TP38/FN0/FP0/TN81（合成信号）。

**3. 没有 IMU 也能测到夜醒**

板子没有板载 IMU，那睡着之后怎么知道人醒了？
用"呼吸规律度塌缩"来判：醒来说话、翻身，就没有周期性呼吸了，自相关的峰会消失。
`reg < 0.35` 加上迟滞就判定夜醒。有 IMU 的话是两条路做 AND 融合。

**4. 音频在端侧实时合成，不存音频文件**

白噪、粉噪、棕噪都是算出来的（xorshift32 PRNG + Kellet 滤波器做粉噪，一阶积分做棕噪），
**Flash 占用 0KB**。16MB Flash 本来也存不下几条 WAV，而且这样还避开了音频编解码崩溃的风险。

入睡后淡出用等功率曲线（人耳听感上才是匀速的），末段线性精确归零，
中途释放音量闪避也不会反弹 —— 任何一下音量突变都会把人弄醒。

**5. 手表界面（LVGL 9）**

两个页面：**表盘页**（大时间、今晚几点自动开始、一个「开始哄睡」按钮、昨晚简报）
和**哄睡页**（三层呼吸光晕、当前阶段、噪声类型 + 已用时）。

能点的只有两处：点「开始哄睡」立刻切页（不等后台确认，手感上不能有延迟）；
点「返回」只回表盘、**哄睡继续跑**（设备在哄睡中途被按回表盘，不该顺手把声音
和判定一起停掉），按钮这时改写成「回到哄睡」；**长按「返回」才是真的结束今晚**。

这块屏是 AMOLED，纯黑像素不发光，所以底色用 `000000`，文字和光晕只用暖色
（约 2700K），睡着后整屏压暗不再更新文字。中文字体是从文泉驿微米黑裁的，
只含界面用到的字（LVGL 自带的 montserrat 不含 CJK，直接用会全是方块）。

真机上磨了两处性能/时序，都有实测数据：触摸是**后到设备**（FT6146 开机后约
23 秒才注册 `/dev/input0`，而 LVGL 15 秒就起来了），改成运行期探测补挂；
帧率从 **5 fps 修到 25 fps**，根因是 `lv_label_set_text()` 每帧无条件标脏。
细节见 [`docs/手表界面_真机验证_20260915.md`](docs/手表界面_真机验证_20260915.md)。

**6. 语音对话能力**

小智（xiaozhi-esp32）的固件是 ESP32-S3 专用的，搬不过来，
但它的架构是"设备薄、服务器厚"，所以我们在 PC 上写了个网关替板子说那套 WebSocket 协议，
板子就等于一台小智设备。板子没有 WiFi，走串口（就是烧录用的那根线，一根线两用）。

**7. 记住你的睡眠习惯**

180 天滚动档案，记录入睡潜伏、夜醒次数、什么手段最管用（棕噪 / 粉噪 / 呼吸引导），
全部在端侧，断网也能用。

## 怎么跑

```bash
mingw32-make test    # 465 条断言（PC 上直接跑，不需要硬件）
mingw32-make app     # 真机主循环 + HAL 模拟后端，跑完整晚（22:30 → 07:10）
mingw32-make demo    # 单晚压缩演示
```

Linux/macOS 直接 `make test` 就行；Windows 用 `mingw32-make`（Makefile 会按
平台自动挑 `gcc`，不用手动传 `CC`）。**没装 make 也能跑**：

```bash
python tests/pc_build.py report    # 等价 make report
python tests/pc_build.py app       # 等价 make app
```

真机上编译烧录看 [`board/README.md`](board/README.md)。

## 目录

`app/mianyu/` 就是 openvela 的应用包本体，会被
[`contest2026_485_xiaomingTV.xml`](contest2026_485_xiaomingTV.xml) 的 `<linkfile>`
映射到 openvela 树里的 `packages/demos/contest2026_485_mianyu` —— 所以包内的
相对路径（`src/` `hal/` `ui/` `include/`）和 CMakeLists 里的是同一套，改的时候别拆开。

| 路径 | 里面是什么 |
|---|---|
| `app/mianyu/` | 应用包：`mianyu_app_main.c`（真机主循环）+ `src/`（核心算法层 6 个模块）+ `include/` + `hal/`（两个后端）+ `ui/`（手表界面与字体）+ 构建文件 |
| `board/` | 板级集成源码（音频通路 bring-up + 串口语音链路）+ 云机构建集成存档；见 [`board/README.md`](board/README.md) |
| `tests/` | 465 条单元测试 + `pc_build.py`（无 make 环境下的构建驱动） |
| `demo/night_demo.c` | 单晚压缩演示 |
| `skills/` | 3 个自定义 Skill：sleep-onset / night-wake / sleep-review |
| `docs/` | 真机运行证据、界面真机验证、测试记录表、首启检查清单、框图 |
| `logs/` | AI Coding 协作记录 + 板上启动日志原文 |
| `contest2026_485_xiaomingTV.xml` | 专属仓 manifest：把本仓 `app/mianyu` 链到 openvela 的 packages 下 |

## 真机现在什么情况

过程和数据都在 [`docs/真机运行证据_20260914.md`](docs/真机运行证据_20260914.md)、
[`docs/手表界面_真机验证_20260915.md`](docs/手表界面_真机验证_20260915.md)
和 [`docs/测试记录表.md`](docs/测试记录表.md)。

跑通的：核心算法和界面进了固件并在板上运行、**手表界面两个页面都建起来了且触摸可用**、
串口语音链路 20 秒零丢帧、板载麦克风采集（12 秒真人环境音）、
板子到网关到服务器的识别链路、整晚闭环模拟（9 小时压缩到 11.8 秒跑完）。

**喇叭没出声**。声学回环对照算下来 B/C=0.83（功放开和关没区别），
说明麦克风收到的 1kHz 是板内电耦合而不是声波 —— 板上喇叭座 J0101 是空的，还没插喇叭。
这是硬件缺件，不是软件问题。

**界面上还没做的**：屏幕肉眼确认。串口能证明对象建好、渲染循环健康、触摸挂上，
证明不了"眼睛看到的是对的那一幅画"。另外板级日志里有一条
`[co5300][readback] ... NO MATCH -> pixel data is not landing`，各版本固件都有；
大概率是 QSPI 模式下 GRAM 读回本来就不受支持导致的**假警报**（同一份日志里
面板 ID 在 4 个字节偏移上错位重复，是读通路有位移的典型样子），但我不靠猜把它写成
"屏是好的" —— 上电看一眼开机闪色就能定论，方法写在上面那份界面验证文档的第 5 节。

另外真人整夜的入睡判定标定还没做，现在的准确率数据只来自合成信号，报告里如实标了。
