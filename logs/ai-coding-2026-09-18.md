## 这三天做了什么

拿到的输入是一份已经完全跑起来的参赛作品（技术报告 + 源码 + 真机联调记录），
任务是**对着模板做最后检查并收口提交**。真正的产出不是新功能，而是把

### 1. 屏幕「间歇性不发光」——从"判到模组供电侧"改成"已定位并修复"

这是这三天最大的翻转。此前结论是「面板数字侧实测通过、软件侧五轮排除八种假设、
判到模组发光/模拟供电侧」，属于**没有软件解**的悬案。这次换了个思路：不再查"为什么不亮"，
而是查"软件到底有没有把屏当成可用的"。

- 让 AI 先做只读审计：把屏幕链路的每一层（LVGL → lv_nuttx → sf32lb_lcd → co5300 → GPIO）
  列出来，并**用二进制字符串比对确认"当前烧进固件的到底是哪一版源码"**。
  这一步直接推翻了两个前提：本地有几套源码副本、编译进固件的那份和仓里的不是同一套。
- 查到一个**留在产品固件里的取证自检**：`co5300.c` 里那段 v50 自检跑在
  `lcddev_register()` **之前**、约 54 秒阻塞（6 轮 × 8 秒 ALLPON + 1 秒 ALLPOFF）。
  也就是说开机后一分多钟内 `/dev/lcd0` 根本不存在，界面线程在死等 —— 屏上只有测试色在闪，
  **看起来完全像"屏坏了"**。它还会把 VADD/背光拉低再拉高、整屏白闪六次。
- 修法：用 `CONFIG_MIANYU_LCD_V50_SELFTEST` 把那段包起来、默认关闭。
- 顺带查出一处**硬件冲突**：`bsp_pinmux.c` 把 PA10 当"LCD Power En"，
  而 `bsp_audio_test.c` 把**同一个脚**当功放使能 —— 任何把它拉低的代码
  （`bsp_audio_set_amp(0)`、声学回环的 `pa_on=0` 对照项）都会让屏幕掉电，
  而且没有任何路径会重做面板上电。改成功放关闭走 DAC 静音、PA10 只许高。
- 修后实测时间线：`8.5s` 背光 PWM 20kHz 起 → `9.1s` 面板 ReadID=0x331100 与期望一致 →
  `9.1s /dev/lcd0 registered (took 0 retries)` → `11.4s` LVGL 线程就绪 → `14.0s` 首个 putarea
  推出（`done == wrram`、`timeout == 0`）。

### 2. 界面重做 + 一个"字体缺字"的静默 bug

- 用只读 agent 把 LVGL 字体文件（`lv_font_mianyu_16/_32.c`）的 `unicode_list` 解出来，
  得到**精确的可用字符集**。结果发现现有界面有 **12 个字不在字体里**：
  「周二」的"二"、「放松」的「松」、「呼气」的「呼」、"还没有记录"整句……全是方块，
  而且**不报任何错**。
- 把字体重生成流程化：`tools/gen_mianyu_fonts.py` 从 `watch_ui.c` 的字符串字面量里
  **扫出实际用到的字**再交给 `lv_font_conv`，改文案重跑一次即可，不再靠手抄字符集。
- 界面重做：由"三页"更正为**两个整页**（表盘 / 哄睡），并新增**语音状态显示**
  （空闲 / 在听 / 在想 / 在说，小圆点随状态呼吸）。状态由 PC 侧网关判定后经
  `CMD_UI_STATE(0x0B)` 下发 —— 板子只看得到串口上有没有音频，分不出是用户在说还是 AI 在说。

### 3. 语音链路的一串 bug（都是"看起来正常、其实没生效"那一类）

| 现象 | 真因 | 修法 |
|---|---|---|
| 麦克风越调越轻 | 采集增益写成 36dB，**超出该 HAL 的合法上限 30dB**，函数直接 `return HAL_ERROR`、寄存器一个字节都不写，增益停在默认 0dB | 改 30dB，并在固件里加"设失败就回落到合法值 + 把实际生效值报给 PC" |
| 每 10 秒断一次线 | `CMD_SET_VOL` **漏在 import 列表外**，而它只在"距上次发音量超过 10 秒"时才走到，于是每 10 秒抛一次 `NameError` 打断整个异步循环 | 补 import，并加**启动自检**：协议常量缺一个就在启动时点名退出 |
| 音量命令从来没生效 | 同上（`NameError` 发生在求值参数时，命令根本没发出去） | 同上；另修掉心跳被"值没变就不发"的去重吃掉的问题 |
| AI 打断自己 | 播报时"关麦"命令混在下行音频洪流里丢了（实测 CRC 错约 1 次/秒），麦克风一直开着把喇叭声收回去，VAD 判成用户在说话 | 改由**板子本地判定**"最近 200ms 是否收到下行音频 或 环里还有货"，不经链路、不会丢 |
| 上行永久静音 | 我自己引入的：判据用 `g_play_type == AUD_PCM`，而它是**黏的**，放完没人发停播命令就一直停在 PCM | 换成上面那个无状态判据 |
| 噪一声就被当成人说话 | ASR 对非语音不报错而是回一个标点（实测拿到过「.」「I.」「I'm stuck.」），拿去问 LLM 会一本正经回一句哄睡话术 | 要求识别结果**至少含一个汉字** |

### 4. 下行"一卡一卡"——量出来的，不是猜出来的

沿"听感 → 现象 → 数据"一路收窄，每步都有实测数字：

- 先取板载 `bsp_audio_play_pending()`（播放环 head−tail）作判据，实测**长期贴在 0**，
  说明播放端一直在"读空气"。
- 再量链路：同样 32KB/s 的平均速率下，**1024 字节一片突发只有 37% 到达板子的解析器，
  64 字节一片均匀发是 100%** —— 板子对突发极敏感。
- 又量到一个更本质的点：DMA 是**按半缓冲消费**的，每次半传输中断一次性取走
  `AUD_HALF_SAMPLES`、不够就补静音，而供料≈实时，于是**断音长度就等于半缓冲时长**：
  1600 样本（100ms）意味着每 100ms 一个 100ms 的洞。改成 480 样本（30ms）后，
  播放环水位从"长期贴在 0"变成稳定 480~960 样本。
- 再把下行从原样 PCM 换成 **G.711 μ-law**（32KB/s → 16KB/s；`voice/ulaw.py` 是权威实现，
  与 C 参考实现解码逐字节一致、往返信噪比 37dB），每轮开头连发 15 帧（900ms）垫底。
- 如实保留的限制：板子播 16kHz/16bit PCM 的消耗速率恰好也是 16KB/s，
  所以**余量来自压缩而不是链路本身**；彻底解决要换串口桥或再压到 ADPCM 4bit。

### 5. 板子日志改走帧协议

板子的 `vllog` 原本用 `syslog()`，而 `/dev/console` 就是语音链路独占的那根 UART ——
每 500ms 一行状态文本直接插进二进制帧流里，实测 6 秒 24 次重同步（4 次/秒）。
改成走 `T_LOG` 帧后累计重同步只有个位数，同时板子的遥测（采集计数、播放环水位、丢帧、
三个屏幕使能脚电平）第一次进了上位机日志。

## 这三天用得比较顺的几件事

- **让 AI 先做只读审计、再动手**：屏幕那条线如果一上来就改代码，会在"软件侧五轮都正常"
  的错误前提上继续打转。先让它把"当前编译进固件的到底是哪份源码"用二进制标记比对确认，
  前提一换，结论就出来了。
- **把"没有报错的失败"当成一类 bug 来查**：麦克风增益、音量、漏 import 这三条症状完全不同，
  但都属于"调用看起来成功了、实际没生效"。后来专门加了启动自检和"设了但没生效"的上报，
  就是为了让这一类不再隐身。
- **先量再说**：下行顿挫从"怀疑环太浅"到"半缓冲粒度"再到"μ-law"，每一步都先拿到数字
  （37% vs 100%、待放 0 vs 480~960），避免了又一轮"改了但不知道有没有用"。
