# 2026-09-14 · 串口语音链路 + 哄睡 app 真正进固件 + 声学回环对照法

## 1. 串口语音链路：一个串口只能有一个读者

### 1.1 为什么走串口而不是 WiFi / BLE
核对原理图与 BOM 后确认：**本板没有 WiFi**（无 RF 网络、无天线、BOM 无 WiFi 模组），
只有 BLE（LCPU 上的 H4 栈）。BLE 传 16 kHz PCM 要自搭 GATT 音频流、带宽也紧张。
而板上现成的 Type-C ①号口就是 CH343 串口（烧录用的那个）——
**一根线既能烧录又能跑数据**。1 Mbaud 下 32 KB/s 单向 PCM 只占约一半带宽，
且语音对话本就基本半双工（要么在听、要么在说），完全够用。

### 1.2 帧协议（2 字节同步头 + CRC，为了能自己找回帧边界）
```
A5 5A | type | flags | seq | len(u16 LE) | payload | crc16(u16 LE)
crc16 = CRC16-CCITT-FALSE，覆盖 type/flags/seq/len/payload
```
串口上板子可能中途复位、USB 可能重枚举，上位机**不能假设"从第一个字节开始就是帧"**。
`seq` 用来统计丢帧率。

### 1.3 踩的大坑：nsh 抢走串口
板子只有一个能通到 USB 的串口（UART1 = `/dev/console`），nsh 会在这个口上
**阻塞 read()**，把 PC 发下来的下行 PCM 抢走。

实测（AI 帮忙写脚本统计）：

| 指标 | nsh 在线时 | nsh 让位后 |
|---|---|---|
| 100 个 PING 回包 | **1 个（1%）** | 正常 |
| CRC 错 | 41 | 1（仅开机握手期） |
| 重同步 | 275 | 3 |

**处置**：把 `CONFIG_INIT_ENTRYPOINT` 从 `nsh_main` 改成自己的入口，
让语音链路独占串口。需要 shell 时 PC 发 `CMD 0x10`，链路把控制台交还 nsh
（有意取舍：交还后下行就不能用了）。

> ⚠️ 这个改动必须**同时**改三处，否则会出现"编译过了但行为不对"：
> ① `configs/nsh/defconfig`（配置源头）② `cmake_out/<board>/.config`
> ③ `cmake_out/<board>/include/nuttx/config.h`。
> **改 defconfig 对 ninja 增量无效** —— `config.h` 只在 cmake configure 时重生成，
> 必须直接改 `config.h` 才能让 `nx_bringup.c` 用新符号重编。这一条是被 ninja
> "什么都没做"坑过一次之后才记住的。

### 1.4 协议自检（开机就跑，不通过不开链路）
```
[vlink] 自检 CRC16-CCITT-FALSE：4 组向量 全部吻合
[vlink] 自检组帧：T_EVENT -> A5 5A 03 00 00 01 00 03 A3 C7 与 PC 侧一致
[vlink] 自检容错：坏 CRC 帧被丢掉，后随好帧仍能解析
[vlink] 自检解析器：整块喂 3/3 帧、逐字节喂 3/3 帧、坏帧容错 —— 全部通过
[vlink] 协议自检全部通过（与 voice/board_link.py 逐字节一致）
```
PC 侧 Python 与板侧 C **逐字节一致**才算过 —— 跨语言协议的差异全在细节里。

## 2. 接 HUGE 坑：哄睡 app 编译了但没进固件（静默符号抢占）

### 2.1 症状
`ninja` 全绿、退出码 0，`libapps_mianyu.a` 也编出来了，
但固件启动日志里只有板级那行 `[vlink] mianyu_main: 产品模式启动`，
**app 的主循环一行都没有**。

### 2.2 根因
板级 `bsp_voice_link.c` 与 app `mianyu_app_main.c` **各自定义了
`int mianyu_main(int argc, char *argv[])`**。`CONFIG_INIT_ENTRYPOINT = mianyu_main`，
链接器解析 init 入口时先撞上板级那个目标文件 —— 于是 app 的
`mianyu_app_main.o` **整个没被从静态库拉出来**，连带 `libapps_mianyu.a` 里
所有成员（7 核心模块 + HAL + UI 字体）全部被丢弃。

**这是最危险的一类 bug：日志有、逻辑无、所有工具都说成功。**

### 2.3 排查手法（AI 协助）
```bash
nm nuttx | grep -E " (T|t) (mianyu_main|vl_product_hold)$"
nm .../mianyu_app_main.c.o | grep mianyu_main   # 看符号出自哪个目标文件
```
再交叉验证体积：修复前后固件 **1,571,940 B → 1,639,192 B，+67,252 B**
——刚好是 app 核心 + HAL + UI 字体的量级。

### 2.4 处置
板级函数改名为 `vl_product_hold()`（仅作兜底：万一 app 没编进来，由它占住
init 线程避免跑飞）。语音链路本就不依赖这个符号 —— 它由
`board_late_initialize()` 里的 `bsp_voice_link_start()` 独立拉起。

修复后 `vl_product_hold` 被 `--gc-sections` 丢弃（无引用）= app 的入口真被选中。

### 2.5 修复后的真机启动日志（节选）
```

[mianyu-ui] LVGL 线程已启动（/dev/lcd0）
==============================================================
 安眠科技 · 主动式哄睡智能体 —— 主循环（HAL 接入版）
 无任何用户指令，全靠 cron + 传感器事件驱动一整晚
==============================================================
```

## 3. 声学回环对照法：怎么判断"喇叭到底有没有出声"

### 3.1 问题
放 1 kHz，麦克风收到强 1 kHz。但这可能是①空气传播的**喇叭声**，
也可能是②**板内 DAC 输出结点 → MIC 通路的电耦合**。两者在频谱上长得一样。

### 3.2 方法：用功放使能当对照组
- **B 组：功放开**（PA10=1）→ 若是①，麦克风应额外收到一份
- **C 组：功放关**（PA10=0）→ 只剩②
- 判据：`C ≈ B` ⇒ 全是电耦合，**喇叭没出声**

**必须先解决方差问题**：单窗读数跳动极大（1 kHz 64 vs 邻近 21~37），
不可判。改成 **12 窗累加（≈0.8 s）**后读数才干净。

### 3.3 结果（多窗平均）
| 组 | 放音 1kHz | 邻近 (750/1250 Hz) | 1kHz/邻近 |
|---|---|---|---|
| B 功放开 | 73.5 | 9.5 | 7.74× |
| C 功放关 | **88.5** | 9.5 | 9.32× |

**B / C = 0.83** —— 关掉功放反而更高。

### 3.4 结论
- 麦克风确实收到很强的 1 kHz（8~9× 邻近，远超 4× 判据）→ **DAC 输出通路是活的**
- 但**功放使能与否没有正向贡献** → 这 1 kHz 是**板内电耦合**，不是声波
- 功放使能后读数略降，符合"功放输入级加载了 DAC 输出结点、串扰略降"的物理直觉
- 已排除：`BSP_ENABLE_DAC2`（LB52 设计禁用）、`EN_OS_DAC`（已开）、PA10（已置位）
- **待确认：接插件 J0101 上是否插了喇叭** —— 当前最可能的原因

> 这个方法的普适价值：**判断"传感器收到的是真物理量还是板内串扰"，
> 可以人为关掉激励链路的一级做对照。**（写进 Skill）

## 4. PC 侧脚本的坑（顺带记两个）

1. **`ModuleNotFoundError: No module named 'serial'`** —— 基础解释器无 pyserial。
   改用隔离 venv（pyserial 3.5）跑，不污染系统环境。
2. **从 `ser.read()` 的二进制 PCM 流里抠日志** —— 板级的 `vllog` 走 syslog 文本，
   **混在 `/dev/console` 的二进制流里，不是独立的 LOG 帧**。
   一开始按"解析 T_LOG 帧"的思路写，什么都抓不到。
   正确做法：读原始字节 → `decode('utf-8','replace')` → 正则抠
   `r"静音 1kHz=(\d+) 邻近=(\d+) ..."`。
   **再进一步**：写进仓的日志必须先过滤掉 `U+FFFD` 行，否则可读性为零。
