# 2026-09-14 串口语音链路、app 真正进固件、声学回环对照

## 1. 串口语音链路

### 1.1 为啥走串口，不走 WiFi 或 BLE

对着原理图和 BOM 看了一圈：**这块板没有 WiFi**，没有射频、没有天线、BOM 里也没 WiFi 模组，
只有 BLE（LCPU 上的 H4 栈）。用 BLE 传 16 kHz PCM 得自己搭 GATT 音频流，带宽还紧张。

板上现成的 Type-C 一号口就是 CH343 串口，也就是烧录用的那个口 ——
**一根线既能烧录又能跑数据**。1 Mbaud 下单向 32 KB/s 的 PCM 只用掉一半带宽，
而且语音对话本来就是半双工的（要么在听，要么在说），够用。

### 1.2 帧格式

```
A5 5A | type | flags | seq | len(u16 LE) | payload | crc16(u16 LE)
crc16 = CRC16-CCITT-FALSE，算 type/flags/seq/len/payload
```

两个字节的同步头加 CRC，是为了让接收方能自己找回帧边界。
板上可能中途复位、USB 可能重枚举，上位机没法假设"从第一个字节开始就是帧"。
`seq` 用来算丢帧率。

### 1.3 踩的坑：nsh 把串口抢了

板上只有一个能通到 USB 的串口（UART1 = /dev/console）。nsh 在这个口上
**阻塞 read()**，PC 发下来的下行 PCM 就被它抢走了。

实测数据：

| 指标 | nsh 在线时 | nsh 让位后 |
|---|---|---|
| 100 个 PING 回包 | 1 个（1%） | 正常 |
| CRC 错 | 41 | 1（只有开机握手那次） |
| 重同步 | 275 | 3 |

办法是把 `CONFIG_INIT_ENTRYPOINT` 从 `nsh_main` 换成自己的入口，让语音链路独占串口。
要用 shell 的时候，PC 发 `CMD 0x10`，链路把控制台交还给 nsh
（这是有意的取舍：交还之后下行就用不了了）。

这个改动得**同时**改三处，不然会出现"编过了但行为不对"：
1. `configs/nsh/defconfig`（配置源头）
2. `cmake_out/<board>/.config`
3. `cmake_out/<board>/include/nuttx/config.h`

光改 defconfig 对 ninja 增量编译没用 —— `config.h` 只在 cmake configure 的时候重新生成，
必须直接改 `config.h`，`nx_bringup.c` 才会用新符号重编。这条是被 ninja
"什么都没做"坑过一次之后才记住的。

### 1.4 协议自检

开机就跑，不通过就不开链路：

```
[vlink] 自检 CRC16-CCITT-FALSE：4 组向量 全部吻合
[vlink] 自检组帧：T_EVENT -> A5 5A 03 00 00 01 00 03 A3 C7 与 PC 侧一致
[vlink] 自检容错：坏 CRC 帧被丢掉，后随好帧仍能解析
[vlink] 自检解析器：整块喂 3/3 帧、逐字节喂 3/3 帧、坏帧容错 —— 全部通过
[vlink] 协议自检全部通过（与 voice/board_link.py 逐字节一致）
```

判据是 PC 侧 Python 和板侧 C 逐字节一致。跨语言写协议，差异全在细节里。

## 2. 最大的坑：哄睡 app 编了却没进固件

### 2.1 现象

ninja 全绿、退出码 0，`libapps_mianyu.a` 也编出来了，
但固件启动日志里只有板级那行 `[vlink] mianyu_main: 产品模式启动`，
**app 的主循环一行都没有**。

### 2.2 原因

板级 `bsp_voice_link.c` 和 app `mianyu_app_main.c` 里各写了一个
`int mianyu_main(int argc, char *argv[])`。`CONFIG_INIT_ENTRYPOINT = mianyu_main`，
链接器找 init 入口时先碰上了板级那个 .o，于是 app 的 `mianyu_app_main.o`
**没被从静态库里拉出来**，连带 `libapps_mianyu.a` 里所有成员
（7 个核心模块 + HAL + 界面字体）一起被丢了。

这类 bug 最麻烦的地方在于：日志有、逻辑没有，而所有工具都告诉你成功了。

### 2.3 怎么查的

```bash
nm nuttx | grep -E " (T|t) (mianyu_main|vl_product_hold)$"
nm .../mianyu_app_main.c.o | grep mianyu_main   # 看符号出自哪个目标文件
```

再用体积交叉验证：改之前 1571940 B，改之后 1639192 B，**多了 67252 B**
—— 差不多就是 app 核心 + HAL + 界面字体的量级。

### 2.4 怎么修的

板级那个函数改名成 `vl_product_hold()`，只当兜底（万一 app 没编进来，
让它占住 init 线程，系统不至于跑飞）。语音链路本来就不靠这个符号，
它是 `board_late_initialize()` 里 `bsp_voice_link_start()` 单独拉起来的。

改完 `vl_product_hold` 被 `--gc-sections` 丢了（没人引用），说明 app 的入口真被选上了。

### 2.5 改完的真机启动日志

```
[audio] PA10 使能（功放 NS4150B）
[mianyu-ui] LVGL 线程已启动（/dev/lcd0）
==============================================================
 安眠科技 · 主动式哄睡智能体 —— 主循环（HAL 接入版）
 无任何用户指令，全靠 cron + 传感器事件驱动一整晚
==============================================================
[09:12:27] 设备就绪，等待睡前时刻
```

## 3. 声学回环对照法：判断喇叭到底出没出声

### 3.1 问题

放 1 kHz，麦克风收到很强的 1 kHz。但这有两种可能：
一是空气传过去的**喇叭声**，二是**板内 DAC 输出结点串到 MIC 的电耦合**。
这俩在频谱上长得一样。

### 3.2 办法：拿功放使能当对照组

- B 组：功放开（PA10=1）。如果是喇叭声，麦克风应该多收到一份
- C 组：功放关（PA10=0）。那就只剩电耦合
- 判据：`C ≈ B` 就说明全是电耦合，喇叭没出声

先把方差问题解决掉：单个窗的读数跳得厉害（1 kHz 是 64，邻近频率 21~37），根本没法判断。
改成叠 12 个窗（约 0.8 秒）之后读数才干净。

### 3.3 结果

| 组 | 放音 1kHz | 邻近 750/1250 Hz | 1kHz/邻近 |
|---|---|---|---|
| B 功放开 | 73.5 | 9.5 | 7.74× |
| C 功放关 | 88.5 | 9.5 | 9.32× |

**B / C = 0.83**，功放关掉反而更高。

### 3.4 结论

- 麦克风确实收到了很强的 1 kHz（比邻近频率高 8~9 倍，远超 4 倍的判据）→ DAC 输出通路是活的
- 但功放开和关对读数没正向贡献 → 这点 1 kHz 是板内电耦合，不是声波
- 功放一开读数还略降，符合"功放输入级加载了 DAC 输出结点、串扰降一点"的常识
- 已经排除的：`BSP_ENABLE_DAC2`（LB52 本来就禁用）、`EN_OS_DAC`（开了）、PA10（置位了）
- 还没确认的：J0101 上到底插没插喇叭，这是目前最可能的原因

这个方法可以推广：**要判断传感器收到的是真物理量还是板内串扰，
就人为把激励链路的一级关掉做对照。**

## 4. 喇叭还没到，先把不靠喇叭的那半条链路验了

### 4.1 网关整链自测（不接板子、不接服务器、不联网）

`selftest_e2e.py`，合成语音灌进假麦克风，跑一遍 VAD → Opus 编码 → WebSocket →
假服务器 → 合成回复 → Opus 解码。六项全过：

```
  [OK] WebSocket 握手 (hello 往返)
  [OK] 音频上行 (Opus 编码已发出)     66 帧 Opus（16k/60ms）
  [OK] VAD 断句 (识别到 2 段语音)
  [OK] TTS 流程 (start/sentence/stop)
  [OK] 音频下行 (Opus 解码+PCM 落库)  87 帧 / 83520 样本
  [OK] LLM 情感字段解析               emotion 事件 2 次
```

先把软件这一整条链排除掉。以后要是"它没反应"，问题就一定在板子上，
不用再从协议、编解码、VAD 这些地方瞎猜。

### 4.2 板载麦克风上行

`listen_voice.py 12 COM6 mic_up2.wav`：

```
   AUDIO_UP    768 帧
   CRC 错 0 / 重同步 29
   196608 样本 = 12.29 秒 @16k
   峰值 4902 / 32767，非零 196359/196608，直流偏置 -0.6
链路验证通过：板子在按协议发真实音频
```

768 帧、0 个 CRC 错，采到 12.29 秒音频。板载这块 MIC 是焊在板上的，不用另外接。

### 4.3 板子 + 网关 + 假服务器

把前两步接起来：`--sink null` 让 TTS 音频收到就丢，正好绕开没喇叭这件事。

```
[serial  ] 已连接 COM6 @1000000 (CH343)
[ws      ] 服务器 hello：下行 24000 Hz -> 已切解码器
[state   ] 聆听中（VAD 自动断句）
```

板子把房间声音采上来 → 网关 VAD 断句 → 送服务器 → 服务器回文本和 TTS。
从板子到"认出说了话"这一段，真机上是通的。

## 5. 遇到的两个环境坑

1. 跑网关连本地 ws 会被系统代理拦成 502（机器上开着 `HTTP_PROXY`）。
   跑之前得 `export NO_PROXY=localhost,127.0.0.1` 并把 `HTTP_PROXY` 之类 unset 掉。
2. 从 `ser.read()` 的二进制 PCM 流里抠日志：板级的 `vllog` 走 syslog 文本，
   **混在 /dev/console 的二进制流里，不是独立的 LOG 帧**。
   一开始按"解析 T_LOG 帧"的思路写，什么都抓不到。
   正确做法是读原始字节 → `decode('utf-8','replace')` → 正则抠。
   写进仓的日志还得先把 `U+FFFD` 那种行滤掉，不然没法看。
